# Icon map generation — design

**Date:** 2026-07-25
**Branch:** `refactor/icon-placeholder-single-source`
**Status:** Approved design, pending spec review
**Related:** issue #1893, PR #1894 (the hand-patch this supersedes)

## Problem

The CLI swaps a component's icons to the user's chosen library (`add` time) by
looking up a central map, `apps/v4/public/r/icons/index.json`
(`canonical lucide name -> { library: icon name }`). That map is **hand-maintained**:

- No build script writes it (`grep -rn "icons/index.json" apps/v4/scripts` is empty).
- It is a git-committed file edited by hand in every icon PR (#1771, #1575, #1894).
- The CLI reads only this map; it does **not** read the `registry/icons/__*__.ts`
  re-export files.

When a component uses a Lucide icon absent from the map, the CLI silently leaves the
Lucide import in place. For non-Lucide libraries this produces broken output — e.g. a
Phosphor project keeps `@lucide/vue` imports or emits an invalid mixed import. That is
issue #1893.

### Root cause

shadcn-vue **ported upstream's map-consuming half but not its map-generating half.**
Upstream (`shadcn-ui/ui`) generates its icon map from a single source of truth via
[`apps/v4/scripts/build-icons.ts`](https://github.com/shadcn-ui/ui/blob/main/apps/v4/scripts/build-icons.ts):
it scans the `IconPlaceholder`-authored base components (which carry every library's
icon name inline) and emits both the `__*__.ts` files and the
`canonical -> { library: name }` mapping. Because the map is *derived from the same
placeholders that render the icons*, a used icon cannot be missing. The #1893 class of
bug is structurally impossible upstream.

shadcn-vue copied upstream's *generated artifacts* — the `__*__.ts` files still bear the
header `// Auto-generated by scripts/build-icons.ts` — but **there is no `build-icons.ts`
in shadcn-vue.** The map became a hand-maintained copy that inevitably drifts. Concrete
evidence of drift already present: the base `Sonner.vue` placeholder declares
`Loader2 -> phosphor SpinnerGapIcon`, but the committed map has `Loader2 -> PhCircleNotch`
— two different icons. The showcase renders SpinnerGap; CLI users get CircleNotch.

## Goal

Port the missing half. Generate the CLI icon map (and the `__*__.ts` files) from the
`IconPlaceholder` source of truth, so the map can never drift from what components use.
Delete the hand-maintained `index.json`. Add a coverage assertion that closes the one gap
upstream doesn't have (shadcn-vue's second, raw-lucide registry).

### Non-goals (YAGNI)

- **No wire-format change.** The served registry stays concrete `@lucide/vue`; manual
  copy-paste output is unchanged. (This was "Approach A" — rejected as more than upstream
  does; upstream's own v4 components ship concrete lucide.)
- **No CLI `add`-time resolver rewrite.** The CLI keeps consuming `index.json` unchanged.
  Only the *provenance* of that file changes: generated, not hand-edited.
- **No rewrite of the 46 `new-york-v4` components** to `IconPlaceholder`. They stay
  concrete lucide; the coverage assertion guards them instead.

## Registry topology (context)

Two parallel component registries, both icon-swapped at `add` time by the same map:

- **`registry/bases/reka/ui/**`** — authored with `IconPlaceholder` (all library names
  inline). `scripts/lib/build-styles.ts` resolves `IconPlaceholder -> @lucide/vue` at
  build and publishes per-style items (`@reka-luma/*`). **This is the map's source of truth.**
- **`registry/new-york-v4/ui/**`** — 46 components with raw `@lucide/vue` imports, served
  as the default `@shadcn` registry. Carries no per-library info, so it can only be
  *validated against* the map, not generate it.

## Architecture

### 1. Generator: `apps/v4/scripts/build-icons.ts`

Deterministic recursive scan (entries sorted by name for stable conflict resolution) of
`registry/bases/reka/**` for `IconPlaceholder` elements. For each element, read the
`lucide` / `tabler` / `hugeicons` / `phosphor` / `remixicon` attributes.

- **Canonical key** = the `lucide` attribute value (every placeholder must have one; a
  placeholder without `lucide` is a warning, matching upstream).
- Build `iconMapping[canonical][library] = value` and `iconUsage[library].add(value)`.
- **Conflict handling:** if the same canonical maps to two different values for a library
  across bases, keep the first (sorted order) and emit a warning. Mirrors upstream.

Vue-specific parsing note: bases are `.vue` SFCs. Attribute extraction can reuse the same
regex approach upstream uses (`<IconPlaceholder ... lib="value" ...>`), or parse via
vue-metamorph's template AST (already a dependency of `scripts/lib/transform-icons.ts`).
Prefer the AST for robustness; the regex is an acceptable fallback and is what upstream ships.

### 2. Phosphor alias resolution

shadcn-vue diverges from upstream in one place: **phosphor placeholders carry aliased
names**, not raw exports. `@phosphor-icons/vue` exports are `Ph`-prefixed, and the project
aliases them to unprefixed `*Icon` names (`export { PhCheckCircle as CheckCircleIcon }`).
tabler / hugeicons / remixicon placeholders already carry raw export names.

The CLI map needs the **raw** phosphor export (`PhCheckCircle`), because the transform
rewrites the import to `from "@phosphor-icons/vue"` where that is the real export.

Derivation rule (consistent across all observed aliases):

```
rawPhosphor = "Ph" + aliasValue.replace(/Icon$/, "")
```

Examples: `CheckCircleIcon -> PhCheckCircle`, `WarningIcon -> PhWarning`,
`CaretDoubleLeftIcon -> PhCaretDoubleLeft`, `XIcon -> PhX`.

The generator applies this rule to produce (a) index.json's phosphor value and (b) the
`__phosphor__.ts` alias line (`export { PhCheckCircle as CheckCircleIcon }`). Because the
rule is a derivation and could in principle produce a non-existent export, **every derived
phosphor name is validated against the installed `@phosphor-icons/vue` package** (see §5).
An optional `phosphor-overrides.json` handles any icon whose real export name breaks the
rule; empty to start.

### 3. Radix: legacy layer (no placeholder source)

`radix` (`@radix-icons/vue`) is a selectable CLI icon library, but the showcase
`IconPlaceholder` has **no `radix` prop** — so radix mappings have no source of truth in
bases and cannot be generated. Dropping them would break radix users.

Resolution (mirrors upstream's own design): keep a small hand-maintained
`apps/v4/registry/icons/legacy-mapping.json` merged into the generated map. Upstream does
exactly this — its `generateIconMapping` reads `registry/icons/legacy-mapping.json` first
"with their lucide/radix values untouched" as a published-CLI compatibility contract, then
layers the scanned mapping on top.

For shadcn-vue this legacy layer holds:
- `radix` values for every canonical (the only library with no placeholder source), and
- any back-compat entries we choose to pin.

Merge order: legacy entries first (order-preserving), scanned entries layered on top for
the five generatable libraries. Radix is never overwritten by the scan (the scan produces
no radix values).

**Alternative considered:** add a `radix` prop to `IconPlaceholder` and to all 166 base
files, making radix fully generated. Rejected for now — large mechanical change, the
showcase does not render radix anyway, and the legacy layer is the upstream-faithful path.
Revisit only if radix showcase support is added.

### 4. Coverage assertion (shadcn-vue's extra registry)

After generation, collect every icon imported from `@lucide/vue` across
`registry/new-york-v4/ui/**` (the raw-lucide registry). Assert each exists as a key in the
generated map (applying the same `Icon`-suffix tolerance the CLI transform uses:
`ChevronDownIcon` resolves via `ChevronDown`). A missing icon **fails the build** with a
message naming the file and instructing the author to add the icon to the relevant base's
`IconPlaceholder`.

This reproduces upstream's structural guarantee across both registries. Fixing #1893
becomes a *consequence*: the six icons already exist in base placeholders (verified —
`Sonner.vue` and `Pagination{First,Last}.vue`), so they flow into the generated map
automatically; the assertion guarantees no future regression.

### 5. Package-name validation

Validate that every generated target name is a real export of its library's package
(`@phosphor-icons/vue`, `@tabler/icons-vue`, `@hugeicons/core-free-icons`,
`@remixicon/vue`, and radix from the legacy layer against `@radix-icons/vue`). This catches
two classes the hand-map cannot: a typo'd name, and a phosphor alias whose derived raw name
doesn't exist. Implemented by importing each package's exports (or reading its `.d.ts`) and
checking membership. Validation failure fails the build.

### Outputs

- `apps/v4/public/r/icons/index.json` — the CLI map (generated; git-tracked artifact).
- `apps/v4/registry/icons/__{lucide,tabler,hugeicons,phosphor,remixicon}__.ts` —
  regenerated, so the "Auto-generated" header stops being a lie.
- Console warnings (missing-lucide, conflicts) and hard failures (uncovered icon, invalid
  package name).

## Data flow

```
registry/bases/reka/**  (IconPlaceholder, all libs inline)
        │  scan + phosphor alias rule
        ▼
   iconMapping (5 generatable libs)  ──merge──►  index.json  ──consumed by──►  CLI transform-icons
        ▲                                           ▲
legacy-mapping.json (radix + back-compat) ──────────┘
        │
new-york-v4/ui/** (raw @lucide/vue) ──asserted-covered-by──► index.json
```

## Edge cases & risks

- **Drift reconciliation.** Regenerating changes some current values (e.g.
  `Loader2 -> PhCircleNotch` becomes `PhSpinnerGap`, matching the showcase). These are
  intentional corrections but are behavior changes for existing users. Mitigation: diff
  generated-vs-committed map, review every delta, and document intentional changes in the
  PR. Where a legacy value must be preserved for compatibility, pin it in
  `legacy-mapping.json`.
- **Phosphor rule breakage.** If a phosphor icon's real export doesn't follow
  `Ph` + stripped-name, §5 validation catches it; `phosphor-overrides.json` resolves it.
- **`.vue` parsing.** Placeholder attributes span multiple lines in some bases; use the
  AST path (vue-metamorph) rather than a single-line regex, or a multiline-tolerant regex.
- **JSON formatting.** The current map is `eslint --fix`-formatted. Generator output must
  match the repo's lint config to avoid noisy diffs (run the same `eslint --fix` step the
  registry build already uses).
- **Determinism.** Sorted scan order + sorted output keys, so regeneration is stable and
  diffs are meaningful.

## Testing strategy

- **Generator unit tests:** given fixture bases with placeholders, assert the produced
  mapping (incl. phosphor alias derivation and conflict warnings).
- **Coverage-assertion test:** a fixture new-york-v4 component using an uncovered icon must
  fail; a covered one must pass.
- **Validation test:** a bogus generated name must fail package validation.
- **Existing `transform-icons` unit tests stay green.** PR #1894's regression test becomes
  redundant (the coverage assertion subsumes it) but may remain.
- **Snapshot/diff gate:** committed `index.json` equals generator output (CI runs the
  generator and fails if the working tree differs — the standard "generated file is stale"
  check).

## Migration / rollout

1. Land `legacy-mapping.json` seeded from the current `index.json` radix values (+ any
   values we choose to pin).
2. Add `build-icons.ts`; wire it into the registry build **before** the styles/registry
   build that consumes the map, plus an npm script for local runs.
3. Run it; diff generated vs committed `index.json`; review and reconcile every delta.
4. Stop hand-editing `index.json`: it remains a git-committed file, but is now produced
   only by the generator. Add a header/README note and a CODEOWNERS or lint hint so nobody
   edits it by hand again.
5. Add the CI staleness + assertion + validation gates.
6. Confirm #1893's six icons resolve correctly end-to-end for phosphor.

## Open decisions for reviewer

1. **Radix:** legacy layer (recommended, upstream-faithful) vs. adding a `radix` prop to
   `IconPlaceholder` + all bases (full generation, larger). Design assumes legacy layer.
2. **`__*__.ts` regeneration:** regenerate them in the same pass (recommended — removes the
   stale "auto-generated" header, one scan) vs. leave them untouched and generate only
   `index.json`. Design assumes regenerate.
3. **#1894:** with generation in place the hand-patch is unnecessary. Close it, or cherry-
   pick nothing (the icons already exist in bases). Sequencing was deferred earlier.
